# Variant Data (SKU) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A color search shows best sellers that really come in the asked color, in that variant's own photo, with no AI guessing; the link opens that variant when the commission is kept.

**Architecture:**
- A new `skuDetails()` in `aliexpress.js` fetches and parses the SKU API, in parallel.
- `pickProducts` gets it as an injected dependency (`skus`), like `pickPhoto`.
- It runs before the photo picker in both color-rescue spots. The picker stays only for listings whose variant colors are codes or missing.

**Tech Stack:** Node.js (ESM), `node:test`, the AliExpress affiliate API.

**Spec:** `docs/superpowers/specs/2026-11-06-sku-design.md`

## Global Constraints
- No paid AI runs: free checks (AliExpress API, stub judges) and unit tests only. The owner tests in Telegram.
- Upload only after the owner says "תעלה". Push `fashion:main` only when `npm test` shows `ℹ fail 0`.
- Every SKU failure (timeout, empty, error) leaves the card exactly as today.
- The price stays "החל מ" with the lowest price (owner's choice).
- A color match shows the variant's own photo (owner's choice).
- Never drop a product because its asked variant is missing from a list of 20 (the API's cap).
- SKU calls: parallel, 3 s timeout, only for the candidates about to be checked.

## Review Focus
1. A request color with no English mapping ("פודרה", "זית"). Expected: no SKU decision; the photo picker decides as today.
2. "לבנות"/"לבנים" meaning for girls/boys. Expected: not read as white (`forWhom`), so no color check.
3. A matching variant without `sku_image_link`. Expected: falls back to the photo picker for that listing.
4. A variant list of exactly 20 with no match. Expected: not dropped; the picker decides.
5. `skus` throws or times out. Expected: the picker runs for all candidates, as today.

### Task 1: Colors from variants

**Files:**
- Modify: `format.js` (new `colorVariant`, next to `COLOR_WORDS`)
- Modify: `bot.js` (`pickProducts` gets `skus`; the two color-rescue blocks; `createBot` default `skus = skuDetails`)
- Test: `test/format.test.js`, `test/bot.test.js`

**Interfaces:**
- Consumes: `skuDetails` (Task 0).
- Produces: `colorVariant(variants: Variant[], request: string) -> { variant: Variant|null, decided: boolean }`.
  - `decided` is true only when the variant names are real (no code like `/^[A-Z]\d?$|^\d+$|color\s*\d/i`), the request's color has an English mapping, and either a variant matches or there are fewer than 20 variants.
- Products rescued this way carry `variant` (for Task 2) and `colorPick: true`.

**Mapping (shopper word → English variant names):**
- שחור → black
- לבן → white
- אדום → red (not wine or burgundy)
- בורדו → burgundy, wine, claret, maroon, bordeaux, "wine red"
- נייבי → navy, "dark blue"
- כחול → blue, navy
- תכלת → "light blue", "sky blue"
- ירוק → green
- צהוב → yellow
- ורוד → pink
- סגול → purple, violet, lavender
- חום → brown, coffee, camel
- בז' → beige, apricot, khaki
- ניוד → nude, beige, apricot, skin
- חאקי → khaki
- אפור → gray, grey
- כתום → orange

The shopper word comes from the same lookup as `colorAlsoLine` (it is `forWhom`-aware).
