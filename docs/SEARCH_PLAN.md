# תוכנית: חיפוש מדויק – "איך זה באמת רשום בעלי אקספרס"

נכתב: 2026-11-02, אחרי סבב בדיקה חי (ראו `docs/TEST_ROUND_2026-11-02.md`).
מטרה: שכל בקשה בעברית תגיע לרישומים החזקים ביותר של הקטגוריה **כפי שהמוכרים באמת רושמים אותם**, בלי ניחושים ובלי תרגום מכונה באמצע.

> הוראה לסוכן שמריץ את זה במחשב המקומי: לעבוד בענף `search-vocab` שנפתח מ־`main`. **לא** להריץ `npm start` עם ה־`BOT_TOKEN` של הבוט החי (מנתק את ה־webhook ב־Render). כל הסקריפטים כאן (`npm run eval:*`) לא נוגעים בטלגרם. לא להעלות ל־`main` בלי אישור הבעלים.

## 1. הבעיה, במילים פשוטות

הזרימה היום:

```
"שמלת ערב שחורה"  ──AI מנחש──►  "black evening dress"  ──►  חיפוש בעלי אקספרס
                                                              │
       כרטיס בטלגרם  ◄── מסננים (AI שופט + כללי קוד) ◄── שמות מוצרים בעברית (תרגום מכונה של עלי אקספרס)
```

שתי נקודות חלשות:

| # | איפה | מה קורה | דוגמה מהבדיקה |
|---|---|---|---|
| A | התרגום לאנגלית | ה־AI **מנחש** איך מוכרים כותבים את המוצר. ניחוש חלש = כל הצינור נשען על בסיס חלש | "חודים לאייפד" נהיה "iPad case"; "מכונת גילוח עם דירוג" נהיה מכונת גילוח פנים |
| B | שמות המוצרים | אנחנו מבקשים מעלי אקספרס שמות **בעברית** (`target_language: "HE"`, `aliexpress.js:70`). זה תרגום מכונה. השופט וכללי הקוד עובדים על העברית הזו | "club dress" → "שמלת מועדון" → השופט קבע "לא שמלת ערב" → שמלה עם 510 מכירות נדחקה לעמוד "עוד". כל case → "כיסוי" → כלל קוד חיפש "מגן" → **אפס** תוצאות ל"מגן לאייפון" |

עיקרון הפתרון: **ללמוד את השפה מעלי אקספרס עצמה** במקום לנחש אותה, ולשפוט לפי השם המקורי של המוכר.

## 2. הפתרון – 3 שכבות (לפי סדר העבודה)

### שכבה 1 – "ללמוד מהמנצחים" (בכל חיפוש, אוטומטי)

אחרי החיפוש הראשון והשיפוט, לוקחים את 3–6 המוצרים **המתאימים** (exact) עם הכי הרבה מכירות, ומהם לומדים:

1. **תת־קטגוריה**: לכל מוצר יש `second_level_category_id` / `first_level_category_id` בתשובת `aliexpress.affiliate.product.query`. התת־קטגוריה הנפוצה ביותר בין המנצחים = הקטגוריה האמיתית של המוצר (למשל "Evening Dresses" ולא "Club Dresses").
2. **מילות המוכרים**: מהשמות המקוריים באנגלית של המנצחים (ראו שכבה 3 – צריך אותם באנגלית) מוציאים את 2–4 המילים שחוזרות הכי הרבה (bigrams/trigrams), למשל `mermaid evening gown`.
3. **חיפוש שני**: `category_ids = <התת־קטגוריה>` + המילים שנלמדו, sort לפי מכירות. התוצאות נכנסות למאגר שהשופט רואה (כמו ה־lists הקיימים ב־`pickProducts`), לא מחליפות אותו.

איפה בקוד:
- `aliexpress.js` → `searchProducts`: לוודא שהשדות `first_level_category_id`, `second_level_category_id` נשמרים על כל מוצר (לבדוק בתשובה אמיתית מה בדיוק חוזר).
- `bot.js` → `pickProducts` (שורה ~178): אחרי `judge()` הראשון, שלב "learn" שבונה `{ categoryId, phrase }` ומריץ `fetchLists(phrase, [{ category: categoryId }, { category: categoryId, sort: "relevance" }])`, ואז שיפוט רק על המוצרים החדשים (כמו ה־second chance הקיים, שורות ~241–250).
- תקציב זמן: רק אם `Date.now() - started < SECOND_CHANCE_BUDGET_MS`.

בדיקת קבלה: על 30 החיפושים של §5 – precision@4 של `eval:search` לא יורד, ובחיפושי בגדים/סגנון ממוצע המכירות של 4 המוצרים בכרטיס הראשון עולה.

### שכבה 2 – מילון קבוע לחיפושים הנפוצים (נבנה פעם אחת, הבעלים מאשר)

קובץ חדש `vocab.json` במאגר:

```json
{
  "שמלת ערב": { "keywords_en": "evening dress long formal", "category_id": 0, "checked": "2026-11-03", "approved": true },
  "מגן לאייפון": { "keywords_en": "iphone case", "category_id": 0, "checked": "2026-11-03", "approved": true }
}
```

(`category_id` = התת־קטגוריה האמיתית מהבדיקה. 0 כאן הוא מקום שמור בלבד.)

1. סקריפט חדש `scripts/build-vocab.js`: לוקח רשימת 200–300 חיפושים נפוצים בעברית (להתחיל מ־`scripts/eval-categories.js`, `scripts/eval-personas.js`, 30 החיפושים מ־§5, ומה ש־`stats.js` שמר כחיפושים אמיתיים), ולכל אחד מריץ את שכבה 1 ושומר מה עבד בפועל: מילים + תת־קטגוריה + 3 מוצרים לדוגמה עם מכירות.
2. הסקריפט כותב גם `docs/VOCAB_REVIEW.md` – טבלה לבעלים: חיפוש → מילים → קטגוריה → 3 דוגמאות. **הבעלים מסמן מה מאושר.**
3. בזמן ריצה (`query.js` → `createUnderstander`): אם הבקשה (אחרי ניקוי "חפש לי", ניקוד, רווחים) תואמת ערך מאושר במילון – משתמשים במילים ובקטגוריה מהמילון, וה־AI רק משלים פרטים (צבע, מידה, מחיר). התאמה לפי ראש הבקשה: "שמלת ערב שחורה עד 200" = "שמלת ערב" + שחורה + מחיר.
4. חיפוש שלא במילון – כמו היום + שכבה 1.

בדיקת קבלה: אותו טקסט ← תמיד אותן מילים ואותה קטגוריה; `eval:query` עובר; אין חיפוש מהמילון שמחזיר פחות מ־4 מוצרים.

### שכבה 3 – שיפוט לפי השם המקורי של המוכר

1. `aliexpress.js`: לבקש `target_language: "EN"` (שורות 70, 107) – השמות יגיעו באנגלית המקורית של המוכרים.
2. השופט (`createRelevanceFilter`, `query.js` ~522) ובדיקת התמונות מקבלים את השם האנגלי.
3. **מה שמוצג למשתמש לא משתנה**: השם הקצר בעברית כבר נכתב היום ע"י ה־AI שלנו (`createTitler` → `short_he`), לא ע"י עלי אקספרס.
4. **זהירות – זה החלק המסוכן**: הרבה כללים בקוד בודקים מילים **בעברית** בשם המוצר. כולם צריכים גרסה באנגלית (או לרוץ על שם עברי שנשמר בנפרד):
   - `format.js`: `PART_TITLE`, `PART_FIRST_WORDS`, `CASE_WORDS`, `SOLD_AS_COVER`, `isPartFor`, `singleForSet`/`SET_TITLE`, `offColor`, `HOLIDAY`/`offTheme`, `SPECIAL_KINDS`/`specialKind`, `LUXURY`/`fakeLuxury`, `modelKey`, `shortTitle`, `dedupeProducts`.
   - `bot.js`: `wrongColor`, `ofBrand`.
   - `query.js`: `honestName`, הנחיות הכותרות (`TITLE_SYSTEM`).
   - הבדיקות ב־`test/format.test.js` ו־`test/bot.test.js` מניחות שמות בעברית – לעדכן/להוסיף מקבילות באנגלית.
   - חלופה בטוחה יותר לשלב ראשון: לבקש **גם** EN וגם HE (שתי קריאות, או קריאה ב־EN ושמירת ה־HE מהקיים) – השופט מקבל EN, הכללים ממשיכים על HE. למדוד קודם את העלות והזמן.

בדיקת קבלה: `npm test` עובר; `eval:search` – precision@4 עולה או שווה; בדיקה ידנית ש"שמלת ערב שחורה" מכניסה את שמלות ה־1,100/510 מכירות לכרטיס הראשון בלי עזרת כללי הסדר החדשים.

## 6. עוד פתוח מהסבב (קטן, בענף נפרד)

- מטען לרכב יופיע רק כשמבקשים "לרכב" (היום הופיע בכרטיס "מטען מהיר").
- תכונה שנכתבה היא חובה ("עמיד במים" – רמקול שולחני הופיע).
- כותרת: לנקות "חפש לי" אם נשאר; Choice / "מותג מוכר" / "חנות רשמית" לא יורדים לשורה לבד.
- מזוודה עד ₪150 – רק מוצר אחד חזר; לבדוק בהרצה חיה באיזה שלב נופלים.
